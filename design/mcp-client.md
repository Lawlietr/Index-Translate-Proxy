# design/mcp-client.md — 把代理接成 agent 的工具：25s 壁壘、截尾偵測的兩條路

> 這檔記錄 `examples/mcp/server.mjs`（MCP client）的設計取捨與**實測證據**。
> 程式在 repo，因為這裡的結論要能重跑（規則 14：結論在 `design/`，可重跑的程式要在 repo）。
> 用法與接法在 `examples/mcp/README.md`，這裡只寫結論與證據。
> 日期：2026-10-13，從本機出口，經**已部署的 Vercel 入口**（`x-proxy-build` 為當時的生產版），不是直打上游。
> 重跑：`cd examples/mcp && npm install && npm run handshake`（不燒配額）；真實翻譯帶 `ITP_KEY` 自己發 `tools/call`。

## 1. 邊界：這個 client 只有一件事是自己的

切塊（規則 4）、強制串流（規則 3）、鑑權（規則 8）、放行清單與 400 文案（規則 1）全部在**代理**那側。
這個 client 不重複實作協定，也不自己拼 prompt 之外的東西。它唯一必須自己做的是：
**把翻譯指令放進 `system`**。AGENTS 事實表「行對應」列寫明——只送編號句不帶指令時，上游會加前言、
把每句展開成多語言列表（3 行→8 行、40 行→7 行），行對應就破掉。所以這裡一律帶指令。

三個方向都測過（en→zh、zh→en、zh→ja）：編號行 **3/3 完整、編號保留**。

## 2. 一律 `stream: true`：Vercel 的 25s 是「開始回」的限制，不是總長度

AGENTS 規則 16 記著 Edge runtime 的「25s 內開始回、可串流到 300s」。這句話在 client 側有一個非显然的後果：

**非串流的 MCP client 要等代理全部組包完才拿到第一個位元組**，所以多塊請求的總時間直接撞上 25s。

同一份輸入（40 行 / 2,990 字元，zh→en，越過 `MAX_INPUT_CHARS=2500` 所以代理切了塊）：

| client 形態 | 結果 |
|---|---|
| 非串流（改之前） | 16.3s 成功一次、18.3s 成功一次、**25.5s → 504** |
| `stream: true`（改之後） | **44.9s → 200，40/40 行完整**、無缺號、順序正確，回傳自報「完整（代理切了 2 塊再接回）」，tokens 1869/1984 |

那個 504 的 body 是 **"An error occurred with your deployment"** —— 是 **Vercel 的錯誤頁**，
不是上游 openresty 的 504（上游的 504 是非串流超過 10s 才出現，見事實表「逾時」列）。
判別方法是看 body 是誰的文案，不是看 status：**兩個 504 是不同的東西**。

所以这不是「上游慢」，是**選錯協定形態會自己撞上平台的牆**。現在這個 client 走 SSE。

## 3. 同一个規則 4，兩條路看到的截尾不一樣（這是本專案自己的一個缺口）

規則 4 要求檢查 `finish_reason === "length"`。查下去發現：

- **非串流組包**：top-level 的 `finish_reason` 取的是**最後一塊**（`src/lib/stream.js:171`）。
  「哪塊被截」在標頭 `x-proxy-chunk-truncated`（`src/worker.js:313`）。→ 中間塊被截時，**只看 body 會漏掉**。
- **串流**：**不帶** `x-proxy-chunk-truncated` 這個標頭，但每塊的 SSE 事件原樣透傳，
  所以**每一塊**的 `finish_reason` 都在流裡。實測看到 `["stop","stop"]`（兩塊各自的值）。

對照之下，走 SSE 反而比看標頭更完整——這是改協定形態順帶得到的，不是原計畫。
**這個缺口沒動協定碼**：資訊沒丟（在標頭裡），而規則 6 明確不允許把上游的東西包進 body。
要讓只看 body 的 client 也拿到，就得改回應形狀 → 那是協定變更，尚未決定，所以這裡只記錄、不排進 TODO。

順帶一條**量測教訓**：我第一版測試用 `/truncated/` 掃整個回應文字來判斷有沒有截尾，結果誤報——
那 40 行的**譯文本身就含 "truncated"**（測試文本講的就是截尾）。判斷要讀結構欄位與標頭，
不要掃自然語言。

## 4. `usage` 是逐塊的，累加才對（已核對，不是推定）

規則 9 會補 `stream_options.include_usage`，所以流裡**每一塊都有一個 usage 幀**。
拿一份抓下来的原始 SSE（`x-proxy-chunks: 2`）數：兩個幀 `1427/1641` 與 `370/350`，
累加 = **1797/1991**；同一輸入走非串流時，代理自己聚合出的也是 **1797/1991**。兩側一致 →
client 累加是正確的，回報的用量不是部分值。（我第一版寫成「覆蓋寫」，那會只留最後一塊的數字。）

## 5. 模型：速度差距有實測，品質沒有

串行精確計時（上游近乎串行，併發量不出東西——事實表「配額」列），3 行短文本，三者的行對應都是 3/3：

| 模型 | 用時 | 倍率 |
|---|---|---|
| `Index-Translate-35B-A3B`（預設） | 1,351ms | 1× |
| `index-mt-9b` | 681ms | 2.0× |
| `index-mt-2b` | 428ms | 3.2× |

與 `design/model-allowlist.md` §2 那輪（1,385 / 583 / 316ms）方向一致。
工具的描述因此寫「快約 2 倍」而**不寫品質**——品質沒評量過，不能順著速度推。
預設不指定模型（用代理清單第一位），要速度才显式帶 `model`。

不放行的 `index-mt-9b-syllable` 經這個 client 送出 → 本地 400，訊息附可用清單與挡掉原因（規則 1）；
缺 `to` → 本地用法錯誤，不燒上游配額（規則 5 的「本地先擋」在 client 側的對應）。

## 6. 機敏資訊：key 的處理（AGENTS 規則 17）

repo 是公開可讀的鏡像（規則 12），所以 key 的邊界要寫成可執行的東西，不是一句提醒：

1. `server.mjs` 不寫死 key，只讀環境變數 `ITP_KEY`／`ITP_BASE`（後者未設時退回 README 那份部署）。
2. 範本是 `mcp.json.example`，**值留空**（照 `.dev.vars.example` 的既有模式）。
3. 真實那份 `examples/mcp/mcp.json` 已進 `.gitignore`。
4. `npm run lint:secret`（已進 CI 第一步）掃 git 追蹤的檔案：64 位 hex（`openssl rand -hex 32` 的形狀）
   與 `ITP_KEY=<真值>` 的赋值。git 的 commit sha 與測試裡的假 sha 都是 40 位 → 不在這個形狀裡，不誤報。
   **負向測試做過**：對真正的 client 設定檔跑它 → 紅，抓到 2 處 64-hex。這才是它有效的證明，
   而不是「現在是綠的」。

## 7. 未證明／要当心

- **翻译品質**完全沒評量（只驗了行對應與完整性）。不要從「行數對」推「翻得好」。
- **併發**沒測過：多個 agent 同時叫這個工具時，代理的 per-instance 併發閘（規則 7）會怎麼表現，未知。
- **client 會快取 tools/list**：改完 `server.mjs` 的描述或參數，正在跑的 client 看到的還是舊版。
  這次就差點被它騙——pi 顯示的描述裡還有舊的簡體字，而檔裡早就改好了。
  驗 client 行為之前先重啟 client，否則**測的是舊檔**。
- 這裡的數字是**某一天的快照**（跟事實表一樣會漂移）。上游有撤回模型名稱的先例（`index-homura-*`），
  所以模型清單要看 `index_translate_models` 的即時回傳，不要看這檔。
